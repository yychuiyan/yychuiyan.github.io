第20章 · 表与索引深度 ​

本章目标 ​

第4章讲了建表语法，第9章讲了索引基础。这一章深入底层：

  1. 了解 Oracle 的各种表类型及适用场景——堆表、IOT、临时表、聚簇表
  2. 理解高水位线（HWM）——为什么 DELETE 不回收空间
  3. 搞清楚 PCTFREE 和 PCTUSED 在块中如何协作
  4. 看懂 B*Tree 索引的根枝叶结构——索引怎么查找一行数据
  5. 知道位图索引为什么只能在数据仓库用

这是第四篇的最后一章。表与索引是每天打交道最多的对象，理解它们的内部机制，才能做出正确的设计选择。

20.1 表的类型 ​

20.1.1 堆表（Heap Table）——默认表类型 ​

你之前建的 students、courses 都是堆表。"堆"的意思是：行随机存放，哪里的块有空位就往哪里塞。

堆表的存储特点：

INSERT 第1行 → 块A 有空位 → 存块A
INSERT 第2行 → 块B 有空位 → 存块B
INSERT 第3行 → 块A 还有空位 → 存块A
...

行的物理顺序和插入顺序没有必然关系。

堆表是最通用的类型，适合绝大多数 OLTP 场景。

20.1.2 索引组织表（IOT——Index Organized Table） ​

IOT 把数据和索引合二为一，行直接存在 B*Tree 索引的叶节点里。

IOT 的好处是主键查询减少一次 I/O（不需要 ROWID 回表），但非主键查询反而变慢。

sql
CREATE TABLE iot_students (
  student_id NUMBER(8),
  name       VARCHAR2(50),
  major_id   NUMBER(4),
  CONSTRAINT pk_iot_students PRIMARY KEY (student_id)
) ORGANIZATION INDEX;  -- 关键：指定为 IOT

适用场景：主键查询为主、数据量不大、很少按非主键字段查询。比如：配置表、字典表、只通过 ID 查的实体表。

20.1.3 临时表（Temporary Table） ​

临时表的数据只对当前会话或事务可见，会话结束后自动清空。

sql
-- 事务级临时表（COMMIT 或 ROLLBACK 后清空）
CREATE GLOBAL TEMPORARY TABLE tmp_calc (
  id NUMBER,
  value VARCHAR2(100)
) ON COMMIT DELETE ROWS;

-- 会话级临时表（会话断开后清空）
CREATE GLOBAL TEMPORARY TABLE tmp_session_data (
  id NUMBER,
  value VARCHAR2(100)
) ON COMMIT PRESERVE ROWS;

使用示例：

sql
-- 存储过程中放中间计算结果
INSERT INTO tmp_calc SELECT ... FROM ... WHERE ...;
-- 用 tmp_calc 做中间表 JOIN...
COMMIT;  -- 数据自动清空，不占空间

临时表的特点：

  • 数据私有：会话A 看不到会话B 的临时表数据
  • 不产生 Redo（对数据本身）：临时表数据的 DML 只记少量 Redo
  • 自动清空：不会累积历史数据

20.1.4 聚簇表（Clustered Table） ​

把经常一起查询的多张表，按关联键预存到同一个数据块中。

查询"软件工程专业的全部学生"时，只需要读一个数据块！但 INSERT 变慢了——因为新行必须放在正确的聚簇块中。

聚簇表用得少。大多数场景用普通表 + 索引 + JOIN 就够。除非你有极端高频的特定关联查询且性能是瓶颈。

20.2 高水位线（HWM）——为什么 DELETE 后空间不回来 ​

20.2.1 什么是高水位线 ​

高水位线（High Water Mark）标记了表曾经达到的最大存储边界。

表中数据块：

全表扫描 = 块1 → 块6（HWM 以下全扫，不管有没有数据）

全表扫描时，Oracle 会从第一个块一直读到 HWM 标记的位置。HWM 之后的空间不会被扫描到。

20.2.2 DELETE 和 TRUNCATE 的天壤之别 ​

sql
-- 插入 10000 行 → HWM 升高到 10000 行对应的位置
INSERT INTO test SELECT ...;  -- 10000 rows

-- DELETE 删除 5000 行 → 数据没了，但 HWM 不变！
DELETE FROM test WHERE ROWNUM <= 5000;

-- 此时 SELECT COUNT(*) 需要扫描到 HWM
-- Oracle 仍然要扫描 10000 行对应的数据块（虽然其中 5000 个是空的）
-- 查询速度没有任何改善！

-- TRUNCATE → HWM 重置到 0
TRUNCATE TABLE test;
-- 空间释放，HWM 归零，全表扫描瞬间完成

这是 DELETE 和 TRUNCATE 最本质的区别：DELETE 降低数据量但不降低 HWM；TRUNCATE 重置 HWM。所以"清空数据"用 TRUNCATE，不要用 DELETE。

20.2.3 如何降低 HWM ​

sql
-- 方法1：TRUNCATE（最快，但全表清空）
TRUNCATE TABLE test;

-- 方法2：MOVE 表（重建表，需要重建索引）
ALTER TABLE test MOVE;

-- 方法3：SHRINK（在线收缩，需要行移动功能）
ALTER TABLE test ENABLE ROW MOVEMENT;
ALTER TABLE test SHRINK SPACE;

-- 查看 HWM 信息
SELECT blocks, empty_blocks, num_rows
FROM user_tables WHERE table_name = 'TEST';

20.3 PCTFREE 和 PCTUSED——块空间的"调节阀" ​

20.3.1 PCTFREE——预留空间给 UPDATE ​

每个数据块中，PCTFREE 控制留多少空间给已有行的膨胀。

PCTFREE = 10（默认）：

块填到 90%（100% - PCTFREE）后，Oracle 不再往里插新行。但已有的行可以在这 10% 的空间里增长（比如 VARCHAR2 字段变长）。

PCTFREE 设置建议：

表类型PCTFREE原因
只读表 / 日志表0没有 UPDATE，空间全用于 INSERT
普通业务表10（默认）适中的更新需求
频繁 UPDATE 长字段的表20~40行膨胀需要更多空间

20.3.2 PCTUSED——什么时候重新"开门" ​

PCTUSED 控制块何时可以重新插入数据。只有块的已用空间降到 PCTUSED 以下时，才重新接受 INSERT。

PCTUSED = 40：

  插到 90% 满 → 停止插入
  用户 DELETE 一些行 → 空间降到 38%（< 40%）
  → 块重新变为"可插入"状态

Oracle 默认使用自动段空间管理（ASSM），此时 PCTUSED 参数被忽略，Oracle 用位图管理空闲空间，不需要手动调。

20.4 B*Tree 索引——结构详解 ​

第9章画了 B*Tree 的示意图，这里补充查找过程的细节。

20.4.1 索引查找——以 student_id 等值查询为例 ​

查找: student_id = 2024002

B*Tree 结构：

查找过程：

  1. 根节点：2024002 ≤ 2024003 → 走左枝
  2. 枝节点：2024002 命中键值 → 走对应叶子
  3. 叶节点：找到 2024002 → 取出 ROWID → 直接读数据块总共 3 次 I/O（根→枝→叶） + 1 次表访问 = 4 次 I/O

20.4.2 范围扫描——叶链表的威力 ​

sql
SELECT * FROM students WHERE student_id BETWEEN 2024003 AND 2024007;
1. 用根→枝→叶定位到 2024003 所在的叶节点
2. 沿着叶节点之间的双向链表向右遍历
   2024003 → 2024004 → 2024005 → 2024006 → 2024007
3. 每找到一个 ROWID，读对应数据块

这就是 B*Tree 索引适合范围查询的原因——叶节点之间有链表相连，找到起点后可以顺序遍历，不需要再回到根节点。

20.4.3 索引的唯一扫描 vs 范围扫描 ​

执行计划中常见的索引访问方式：

执行计划中的字样场景效率
INDEX UNIQUE SCANWHERE pk = 值（主键等值）最高
INDEX RANGE SCANWHERE pk > 值 或 BETWEEN高
INDEX FULL SCAN扫描整个索引（比全表扫描快，因为索引更小）中
INDEX FAST FULL SCAN像读表一样多块读取索引中
INDEX SKIP SCAN跳过复合索引的前导列较低
sql
-- 查看索引的使用方式
EXPLAIN PLAN FOR
SELECT * FROM students WHERE student_id BETWEEN 2024003 AND 2024007;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

20.4.4 索引什么时候失效 ​

场景原因
WHERE UPPER(name) = 'ZHANGSAN' 且只在 name 上有索引索引存的是原值，不是 UPPER() 的结果（需要函数索引）
WHERE name LIKE '%三'（前导模糊）索引按值排序，前导通配符无法定位起点
WHERE score + 10 > 90（对列做运算）索引存的是 score，不是 score + 10
WHERE name IS NULLB*Tree 索引不存 NULL 值
复合索引 (A, B) 但 WHERE B = 1跳过了最左列 A

20.5 位图索引为何不适合 OLTP ​

第9章提过这个概念，这里解释底层原因。

20.5.1 位图索引的存储结构 ​

bmp_idx_gender 的内容：

gender='M': [1,0,1,0,1,0,0,1]  → 指向所有 M 的行
gender='F': [0,1,0,1,0,1,1,0]  → 指向所有 F 的行

一个键值的位图覆盖一个数据块范围内的所有行。

20.5.2 致命的并发问题 ​

当两个会话同时插入不同性别的行时：

会话A: INSERT INTO students (gender) VALUES ('M');
  → 需要修改 gender='M' 的位图

会话B: INSERT INTO students (gender) VALUES ('F');
  → 需要修改 gender='F' 的位图

问题：gender='M' 和 gender='F' 的位图在同一个索引块中！
     → 会话B 等待会话A 释放索引块锁
     → 即使它们插入的是不同 gender 的数据！

位图索引的一个条目锁住的是整个位图段，而不是一行。在 OLTP 高并发写入场景下，位图索引是性能灾难。

记住：位图索引 = 数据仓库专用。OLTP 系统（频繁增删改）看见位图索引就删。

本章小结 ​

知识点核心理解
堆表 vs IOT堆表行随机放，IOT 数据直接存在索引叶节点，主键查询少一次 I/O
临时表会话/事务私有，自动清空，适合中间结果
HWMDELETE 不降低 HWM，全表扫描仍然扫到 HWM，TRUNCATE 重置 HWM
PCTFREE块中预留空间给 UPDATE 膨胀用，只读表应设为 0
B*Tree 查找根→枝→叶定位（3~4次 I/O），叶链表支持高效范围扫描
索引失效函数包裹、前导模糊、列运算、NULL、跳过复合索引前导列
位图索引并发 DML 锁整个位图段，OLTP 绝对禁用

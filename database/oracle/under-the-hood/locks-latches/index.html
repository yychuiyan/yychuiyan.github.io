第18章 · 锁与闩 ​

本章目标 ​

锁是并发控制的执行者。这一章你会理解：

  1. Lock 和 Latch 的本质区别——一个是"排队等叫号"，一个是"原地转圈抢"
  2. DML 锁怎么工作——行锁存哪里、表锁有哪些模式
  3. 外键不建索引 = 全表锁——这个经典问题在第4章提过，现在讲清楚底层原因
  4. 死锁怎么产生、Oracle 怎么自动检测
  5. 怎么查"谁锁了谁"——排查阻塞问题的实用 SQL

第17章讲了 MVCC 如何让读写不互相阻塞，这一章讲的是：当写操作相遇时，Oracle 如何协调——以及你写错代码时会怎么把并发搞砸。

18.1 Lock 和 Latch——两种截然不同的锁 ​

Oracle 中有两种"锁"，但它们的机制完全不同：

特性Lock（锁 / Enqueue）Latch（闩）
保护什么数据库对象（行、表、事务）内存数据结构（SGA 中的链表、哈希桶）
排队机制✅ 有队列，先来后到，FIFO❌ 无队列，先到先得
等待方式排队等待，等不到就睡觉原地自旋（spin）重试，还不行才睡觉
持有时间长（整个事务期间）极短（微秒级）
能否手动控制✅ 可以（SELECT ... FOR UPDATE）❌ 完全由 Oracle 内部管理
查看方式v$lock、v$locked_objectv$latch、v$latchholder

比喻：Latch 像公共厕所的门闩——有人在里面就锁上，你得在外面原地等着（或者过会再来）。Lock 像银行取号——拿号排队，轮到你了自然叫你。

18.1.1 Latch 的工作原理 ​

Latch 保护 SGA 中的内存结构。Oracle 进程在访问某些共享内存前，必须先获取对应的 Latch。

text
进程A 想访问 Library Cache 中的某个链表
  → 获取 Library Cache Latch
  → 获取成功 → 访问链表 → 释放 Latch
  → 获取失败 → spin（CPU 空转）重试
            → 重试 N 次还是失败 → 让出 CPU，sleep 一会再试

Latch 的关键设计：不排队。因为 Latch 持有时间极短（微秒级），排队、唤醒的管理开销比 Latch 本身持有时间还长——不如原地转圈等。这是操作系统层面的经典权衡。

DBA 和开发者一般不直接处理 Latch。如果 v$latch 中某个 Latch 的 miss/sleep 数量持续增长，说明 SGA 存在热点竞争——通常是应用设计问题（比如大量并发执行完全相同的 SQL，导致 Library Cache Latch 争用）。

18.2 DML 锁——你最常打交道的老朋友 ​

18.2.1 行级锁（TX Lock） ​

Oracle 的行锁设计有几个独特之处：

行锁存在数据块里，不在锁管理器里。

数据块头部的 ITL（Interested Transaction List）：

每行数据的行头有一个 lock byte，指向 ITL 中的某个 slot。不需要一个中央"锁管理器"来记录谁锁了哪一行——Oracle 把锁信息直接嵌在数据块里。

这意味着什么？ Oracle 可以锁定任意多行而不需要额外的锁管理开销。没有"锁升级"（Lock Escalation）——不像 SQL Server，当行锁太多时会自动升级为页锁甚至表锁，Oracle 绝对不会自动升级锁粒度。

Oracle 从不升级锁。这是它和 SQL Server 最本质的差异之一。你锁了 100 万行，就是 100 万个行锁，永远不会变成表锁——除非你手动 LOCK TABLE。

行锁只有一种模式：独占（Exclusive）。锁定某行的会话独占这行的修改权，其他会话想改同一行必须等待。

sql
-- 会话A
UPDATE students SET name = '张三丰' WHERE student_id = 2024001;
-- 获取 student_id=2024001 的行锁（TX Lock），不提交

-- 会话B
UPDATE students SET name = '张三疯' WHERE student_id = 2024001;
-- 等待！会话A 还没有释放行锁
-- 会话B 被阻塞，等待会话A COMMIT 或 ROLLBACK

18.2.2 表级锁（TM Lock） ​

DML 操作不仅获取行锁，还会自动获取一个表级锁。表锁的模式决定了其他会话能对这个表做什么。

表锁模式简称获取时机允许并发 DML？允许并发 DDL？
Row ShareRSSELECT ... FOR UPDATE✅❌
Row ExclusiveRXINSERT/UPDATE/DELETE✅❌
ShareSCREATE INDEX 等❌❌
Share Row ExclusiveSRX极少手动使用❌❌
ExclusiveXDROP TABLE、ALTER TABLE❌❌

你不需要手动获取表锁——Oracle 在 DML 时自动获取 RX 锁。RX 锁之间是兼容的——多个会话可以同时对同一张表做 DML，这是 Oracle 高并发的基础。

18.2.3 查看锁信息 ​

sql
-- 查看当前被锁定的对象
SELECT lo.object_id,
       o.object_name,
       lo.session_id,
       lo.oracle_username,
       lo.locked_mode
FROM v$locked_object lo
JOIN dba_objects o ON lo.object_id = o.object_id;

-- 查看谁在等待锁
SELECT sid, blocking_session, wait_class, seconds_in_wait
FROM v$session
WHERE blocking_session IS NOT NULL;

-- 查看完整的锁等待链
SELECT
  waiting_sess.sid AS waiting_sid,
  holding_sess.sid AS holding_sid,
  waiting_sess.seconds_in_wait
FROM v$session waiting_sess
JOIN v$session holding_sess
  ON waiting_sess.blocking_session = holding_sess.sid;

18.3 外键不建索引——经典并发灾难 ​

这是第4章和第9章都提过的问题，现在从锁的角度来解释底层原因。

18.3.1 场景重现 ​

sql
-- students.major_id 是外键，引用 majors.major_id
-- 假设 major_id 上**没有**索引

-- 会话A：删除一个专业
DELETE FROM majors WHERE major_id = 10;

Oracle 执行这个 DELETE 时，需要检查 students 表中是否有行引用了 major_id = 10（外键约束要求：子表有引用时不能删父表）。

如果有索引：

text
1. 查索引：major_id = 10 在 students 中有哪些行？
2. 索引返回：2 行（RID1, RID2）
3. 对这两行加共享锁（防止检查过程中被修改）
4. 确认没有未提交的引用 → DELETE 成功

如果没有索引：

text
1. 全表扫描 students，找 major_id = 10 的行
2. 扫描过程中，对 students 表的**每一行**加共享锁！
   → 因为这个检查必须"读到一致的数据"，Oracle 需要防止别人在扫描过程中插入 major_id = 10 的行
   → 没有索引无法精确定位，只能锁全表
3. 此时，任何其他会话对 students 的 INSERT/UPDATE/DELETE 全部被阻塞！

这就是为什么外键列必须建索引。你少建一个索引，某天有人删了一条父表记录，整个子表的写入就堵死了。

sql
-- 解决方案（早就该做）：
CREATE INDEX idx_students_major ON students (major_id);

18.4 死锁——ORA-00060 ​

18.4.1 死锁是怎么产生的 ​

两个会话互相等待对方持有的锁：

text
时间线：

T1: 会话A 修改 students 第1行 → 获取行锁 L1
T2: 会话B 修改 students 第2行 → 获取行锁 L2
T3: 会话A 尝试修改 students 第2行 → 等待 L2 释放...
T4: 会话B 尝试修改 students 第1行 → 等待 L1 释放...

结果：A 等 B，B 等 A → 死锁！

18.4.2 Oracle 的自动检测 ​

Oracle 自动检测死锁，选择其中一个会话"牺牲"掉，回滚它的当前语句，另一个继续执行。

sql
-- 会话A
UPDATE students SET name = 'A1' WHERE student_id = 2024001;
-- 等几秒...
UPDATE students SET name = 'A2' WHERE student_id = 2024002;
-- 此时如果B已经锁了2024002，A会等待...

-- 会话B（同时）
UPDATE students SET name = 'B1' WHERE student_id = 2024002;
UPDATE students SET name = 'B2' WHERE student_id = 2024001;
-- ORA-00060: deadlock detected while waiting for resource

Oracle 检测到死锁后，牺牲会话B，报错 ORA-00060，同时回滚会话B的当前语句。会话A 获得锁继续执行。

18.4.3 Oracle 中死锁为什么相对少见 ​

原因说明
没有锁升级不会突然从行锁升级为页锁/表锁，不会产生意外的锁冲突
读不加锁SELECT 永远不加锁，大大减少了锁竞争面
行级锁不像某些数据库用页级锁，锁粒度最细

大多数 Oracle 中的死锁，是应用程序显式覆盖了默认锁行为导致的——比如不当地使用 SELECT ... FOR UPDATE。

18.4.4 如何避免死锁 ​

方法说明
统一访问顺序所有事务按相同顺序访问资源（比如都先改表A再改表B）
减少事务持有锁的时间把不相关的操作移到事务外面，尽快 COMMIT
避免不必要的显式锁不要随便 SELECT ... FOR UPDATE
检测并重试捕获 ORA-00060，重试事务

18.5 DDL 锁——保护表结构 ​

DDL 操作（CREATE/ALTER/DROP）需要获取数据字典的排他锁，防止 DDL 和 DML 同时修改同一个对象。

sql
-- 会话A 正在修改 students 表的数据
UPDATE students SET name = '...' WHERE ...;
-- 还没提交

-- 会话B 尝试修改 students 表的结构
ALTER TABLE students ADD (phone VARCHAR2(20));
-- 等待！因为会话A 持有 students 上的 DML 锁
-- 只有等会话A COMMIT 或 ROLLBACK 后，ALTER TABLE 才能执行

反过来也一样——如果某个会话正在执行 DDL（比如重建索引），其他会话对这个表的 DML 也会被阻塞。

18.6 阻塞排查实战 ​

18.6.1 找出"罪魁祸首"——谁锁了谁 ​

sql
-- 完整的阻塞诊断 SQL
SELECT
  blocking.sid      AS 阻塞者SID,
  blocking.serial#  AS 阻塞者序列号,
  blocking.username AS 阻塞者用户,
  blocking.sql_id   AS 阻塞者SQL_ID,
  waiting.sid       AS 等待者SID,
  waiting.username  AS 等待者用户,
  waiting.seconds_in_wait AS 等待秒数,
  waiting.event     AS 等待事件
FROM v$session waiting
JOIN v$session blocking
  ON waiting.blocking_session = blocking.sid
WHERE waiting.blocking_session IS NOT NULL;

18.6.2 找出阻塞者正在执行的 SQL ​

sql
SELECT sid, sql_text
FROM v$session s
JOIN v$sql sql ON s.sql_id = sql.sql_id
WHERE s.sid = &阻塞者SID;  -- 替换为上面查到的 SID

18.6.3 "杀掉"阻塞会话（谨慎！） ​

sql
-- 先查 SID 和 SERIAL#
SELECT sid, serial#, username, status FROM v$session WHERE username = 'SYSTEM';

-- ALTER SYSTEM KILL SESSION
ALTER SYSTEM KILL SESSION 'sid,serial#';
-- 例如：ALTER SYSTEM KILL SESSION '42,12345';

KILL SESSION 只是标记会话为终止，Oracle 不会立即释放资源。被杀的会话需要 PMON 进程去清理。如果等不及，加 IMMEDIATE：ALTER SYSTEM KILL SESSION '42,12345' IMMEDIATE;

本章小结 ​

知识点核心理解
Lock vs LatchLock 有队列（FIFO），保护数据库对象；Latch 无队列（自旋），保护内存结构
行锁（TX）存在数据块 ITL 中，只有一个模式（独占），Oracle 从不升级锁
表锁（TM）DML 自动获取 RX，RX 之间兼容——多个会话可同时改同一张表
外键+无索引DELETE 父表时子表全表加共享锁，阻塞所有 DML——必须建索引
死锁Oracle 自动检测（ORA-00060），牺牲一个会话，程序应捕获并重试
避免死锁统一访问顺序、缩短事务、不滥用显式锁

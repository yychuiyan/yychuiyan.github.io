第19章 · Redo 与 Undo ​

本章目标 ​

Redo 和 Undo 是 Oracle 最底层的两个日志机制。前面的 MVCC、事务、锁、崩溃恢复——全部建立在它们之上。这一章你会理解：

  1. Redo 和 Undo 分别记录什么——一个"向前滚"，一个"向后退"
  2. Change Vector 是什么——Redo 的最小单位
  3. Undo 段如何同时支持回滚、读一致性和事务恢复
  4. 块清除（Block Cleanout）是什么
  5. ORA-01555 的深层原因——不只是 Undo 空间不够

如果说体系结构是 Oracle 的骨架，Redo 和 Undo 就是 Oracle 的血液系统。每一个操作都在两条血管中留下痕迹。

19.1 Redo 和 Undo 是什么 ​

19.1.1 一句话区分 ​

RedoUndo
作用重做——把已提交的变更"重放"一遍撤销——把未提交的变更"倒退"回去
记录什么"怎么把数据变成新版本""怎么把数据变回旧版本"
保护什么已提交的数据（持久性）未提交的数据（原子性+隔离性）
存在哪里Redo Log Buffer → 联机重做日志 → 归档日志Undo 表空间 → Undo 段
什么时候写每次 DML 都写，在修改数据块之前每次 DML 都写，在修改数据块之前
什么时候读崩溃恢复回滚 / 一致性读 / 事务恢复
sql
-- 一条简单的 UPDATE：
UPDATE students SET name = '张三丰' WHERE student_id = 2024001;

-- Oracle 同时生成：
-- Redo："把 student_id=2024001 的 name 改成 '张三丰'"（怎么重做）
-- Undo："把 student_id=2024001 的 name 改回 '张三'"（怎么撤销）

19.1.2 为什么两者都要 ​

有些数据库只有 Redo（没有 Undo），恢复时只能重放到最后——如果最后是未提交的事务，数据就不一致。有些只用 Undo——崩溃后已提交的数据可能丢失。

Oracle 两者都要，因为它们各管各的：

场景1：事务进行到一半，用户 ROLLBACK
  → 只需要 Undo："逆向执行"，撤销每一步

场景2：事务已提交，随后数据库崩溃
  → 只需要 Redo："重放"所有已提交的变更

场景3：崩溃时既有已提交的、也有未提交的事务
  → 先用 Redo 把磁盘恢复到崩溃前一刻
  → 再用 Undo 回滚那些未提交的事务
  → 数据库恢复到一个一致的状态

19.2 Redo 深入 ​

19.2.1 Change Vector——Redo 的最小单位 ​

Redo 日志的最小组成单位是 Change Vector（变更向量），一条 DML 可能产生多条 Change Vector。

sql
UPDATE students SET name = '张三丰' WHERE student_id = 2024001;

产生的 Change Vector：

CV1: 修改数据块 X 的第 Y 行，把 name 从 '张三' 改为 '张三丰'
CV2: 修改 Undo 块 U 的第 V 行，写入 Undo 记录（旧值 '张三'）
CV3: 修改 Undo 段头的事务表，更新事务状态

重要：Redo 不仅记录"数据变更"，也记录"Undo 块的变更"。这保证了即使 Undo 块本身损坏，也能通过 Redo 重建。

19.2.2 Redo Record——一组相关 Change Vector 的集合 ​

多个 Change Vector 被组织成一条 Redo Record：

Redo Record {
  SCN: 1001
  时间戳: 2024-09-01 10:30:00.001
  Change Vectors: [CV1, CV2, CV3]
}

19.2.3 Redo 从生成到归档的旅程 ​

DML 执行
  │
  ▼
Copy Redo 阶段：
  将变更前的数据（Old Value）拷贝到 Undo 块
  (这个 Undo 块的变化也产生 Redo CV)
  │
  ▼
Apply Change 阶段：
  将新值写入数据块（此时块变 Dirty）
  │
  ▼
Redo Records 写入 Redo Log Buffer（内存）
  │
  ▼
LGWR 将 Redo Log Buffer 写入 Online Redo Log（磁盘）
  触发条件：COMMIT / 1/3满 / 3秒 / 1MB
  │
  ▼
ARCn 归档进程将写满的 Online Redo Log 复制到归档日志

19.2.4 为什么要"先记日志再改数据"（WAL） ​

如果先改数据块、再记 Redo 日志：

先改数据：
  1. 改数据块 → 成功！
  2. 记日志... → 崩溃！日志没写成功

结果：数据已经被改了，但没有 Redo 记录。
      如果此时 Undo 块也还没写到磁盘，崩溃恢复时无法判断这个变更是已提交还是未提交。

Oracle 的做法（Write-Ahead Logging）：

先记日志：
  1. 写 Change Vector 到 Redo Log Buffer（"我准备要改这个块了"）
  2. 改数据块

结果：即使数据块在步骤2之后崩溃，Redo Log 中已经有步骤1的记录。
      恢复时根据 Redo 重放步骤2。

关键保证：在 DBWn 把脏块写入数据文件之前，Redo Log Buffer 中对应的 Change Vector 必须先被 LGWR 写入磁盘。这确保了磁盘上的数据永远不会比 Redo 日志"更新"。

19.2.5 Redo 的大小与性能 ​

sql
-- 查看 Redo 日志信息
SELECT group#, sequence#, bytes/1024/1024 AS size_mb, status
FROM v$log;

-- 查看 Redo 生成速率
SELECT name, value
FROM v$sysstat
WHERE name IN ('redo size', 'redo entries', 'redo writes');

Redo 日志太大 → 切换周期长 → 但崩溃恢复时需要扫描的日志也多 Redo 日志太小 → 切换频繁 → 日志切换是额外的 I/O 开销

19.3 Undo 深入 ​

19.3.1 Undo 的三个用途 ​

Undo 段中的数据服务于三个目的：

Undo 的三大职能：

三种用途中，读一致性（MVCC）是最容易被低估的。很多人以为 Undo 只在 ROLLBACK 时用——实际上，每一条 SELECT 都可能用到 Undo，如果它查询的数据块在查询开始后被修改过。

19.3.2 Undo 段的结构 ​

Undo 段
  ├── 段头（Segment Header）
  │   ├── 事务表（Transaction Table）→ 记录所有使用这个 Undo 段的事务状态
  │   └── 空闲块列表
  │
  └── Undo 块（Undo Blocks）
      └── Undo 记录链接成单链表
          记录1（最新）→ 记录2 → 记录3 → ...（最旧）

每个事务在事务表中占一行，包含：

  • 事务 ID（XID）
  • 事务状态（Active / Committed / Aborted）
  • Undo 记录链表的指针
  • 提交 SCN（如果已提交）

19.3.3 Undo 记录的链接 ​

一个事务可能修改很多行，产生多条 Undo 记录，它们被链接成单向链表：

事务 TX-001 的 Undo 链：

Undo 记录3（最新）  → Undo 记录2  → Undo 记录1（最旧）
"把score改回85"      "把name改回张三"  "删除这行"
    ↑                                      ↑
    └──────────── 指针方向 ─────────────────┘
    (每条记录指向更旧的记录)

ROLLBACK 时，从最新记录开始，沿着链表逆向执行。对于 SELECT 的一致性读，Oracle 从最新版本开始，沿着 Undo 链往回找，直到找到目标 SCN 之前的版本。

19.4 块清除（Block Cleanout） ​

19.4.1 什么情况需要块清除 ​

当事务提交时，数据块里的 ITL 条目被标记为"已提交"，但数据块本身不会马上写回磁盘。如果之后另一个事务读到了这个块，它需要确认：ITL 中标记为"已提交"的事务是何时提交的。

这个确认操作就是块清除——把事务的提交 SCN 写到 ITL 条目中。

19.4.2 两种清除方式 ​

方式说明代价
快速清除Undo 段头的事务表中仍有该事务的记录读 Undo 段头，拿到提交 SCN，写入 ITL
延迟清除Undo 段头的事务信息已经被覆盖需要从 Undo 段头找到事务表，再从 ITL 找到 Undo 记录，逐步回溯

如果延迟清除需要的 Undo 也已被覆盖，就会出现 ORA-01555。

19.4.3 为什么 COMMIT 后第一次查询可能产生 Redo ​

块清除本身是一个对数据块的修改（写入提交 SCN），因此会产生 Redo！这就是为什么有时候一个纯 SELECT 操作，竟然会触发 Redo 写入——块清除在悄悄改写数据块。

19.5 Redo 和 Undo 的协作——一个完整的故事 ​

让我们追踪一条 UPDATE 从开始到提交的完整旅程，看 Redo 和 Undo 如何配合：

时间线：UPDATE students SET name = '张三丰' WHERE student_id = 2024001;

如果 Step 4 和 Step 5 之间崩溃：

  • Redo 日志有 Step 4 的 Redo Record
  • 重启后，Oracle 看到此事务的 Redo 但没有对应的 Commit 标记
  • 使用 Undo 回滚此事务 → 数据回到修改前

如果 Step 5 之后崩溃（但 Step 6 之前）：

  • Redo 日志有完整的 COMMIT 标记
  • 重启后，Oracle 从 Redo 中重放 Step 2 和 Step 3
  • 同时重放 Undo 块的变更
  • 数据模块恢复到 Step 3 之后的状态 → 与 COMMIT 时一致

19.6 ORA-01555 再探——这次从 Redo/Undo 视角 ​

第17章从 MVCC 角度解释了 ORA-01555。现在从 Redo/Undo 的角度再深化：

19.6.1 ORA-01555 发生的三个条件 ​

必须同时满足：

  1. 一个长时间运行的查询（比如持续 30 分钟的大报表）
  2. 查询执行期间，它的数据被其他会话修改（新版本产生，旧版本进 Undo）
  3. 这些 Undo 数据被覆盖了（UNDO_RETENTION 太短 / Undo 表空间太小）

19.6.2 延迟块清除导致的 01555 ​

即使没有长时间运行的查询，也可能遇到 ORA-01555：

一个事务修改了大量数据并 COMMIT
  → ITL 中标记为已提交，但没有写入提交 SCN（需要清除）

之后另一个查询扫描这个块
  → 需要做延迟块清除（知道事务的提交 SCN）
  → 去 Undo 段头查事务表
  → 但事务表的信息已被覆盖！
  → ORA-01555

解决这类 ORA-01555，需要在批量 DML 后手动执行 COMMIT 不必做什么——实际上应该分批提交，并且每批提交后让 Oracle 有时间完成块清除。

本章小结 ​

知识点核心理解
Redo 是什么"重做日志"——记录怎么把数据变成新版本，保证持久性
Undo 是什么"撤销日志"——记录怎么把数据变回旧版本，服务于回滚+读一致性+事务恢复
Change VectorRedo 的最小单位，一次 DML 产生多条 CV
WAL 原则在数据块写入磁盘前，对应的 Redo 必须先写入磁盘
Undo 三大用途事务回滚、读一致性（MVCC）、事务恢复（SMON）
块清除将提交 SCN 写入 ITL，清除操作本身也产生 Redo
ORA-01555（Redo/Undo视角）Undo 被覆盖 → 一致性读失败或延迟块清除失败

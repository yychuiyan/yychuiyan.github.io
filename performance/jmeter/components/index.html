核心元件详解 ​

逐一拆解 JMeter 的八类元件，搞懂每种元件干什么、怎么选、什么时候用。

回顾第一章的口诀——配前定，取后断听。八类元件按执行顺序排列，这一章也按这个顺序来讲。

线程组 (Thread Group) — "多少个用户，怎么来" ​

线程组定义了压测的用户模型：多少人、怎么启动、跑多久。

标准线程组 (Thread Group) ​

右键 Test Plan → 添加 → 线程（用户）→ 线程组

参数说明怎么设
线程数并发用户数从小到大递进，别上来就填 1000
Ramp-Up 时间（秒）启动全部线程的耗时建议 = 线程数 ÷ 5，比如 50 线程设 10 秒
循环次数每个线程跑几轮调试填 1~3；正式压测勾"永远"+ 设持续时间
调度器 → 持续时间总运行时长基准测试 60 秒，稳定性测试 10~30 分钟

setUp / tearDown 线程组 (setUp / tearDown Thread Group) ​

这两个是"辅助线程组"，不参与主体压测统计：

setUp 线程组 (setUp Thread Group)    → 最先执行，只跑一次。用来做登录、准备测试数据
  普通线程组                          → 主体压测
tearDown 线程组 (tearDown Thread Group) → 最后执行，只跑一次。用来做清理、登出

就算普通线程组报错停止了，tearDown 也会执行，保证清理逻辑不会漏。

插件线程组 (Custom Thread Groups) ​

JMeter 5.5 以上已内置 Plugins Manager，直接装插件就行：

菜单栏 → Options → Plugins Manager → Available Plugins → 搜索 Custom Thread Groups → 勾选 → Apply Changes and Restart

装完后再右键线程组就能看到这些新类型：

类型一句话典型场景
Concurrency Thread Group阶梯式加压"从 10 人每分钟加 10 人，一直加到 100，看系统什么时候崩"
Ultimate Thread Group多波次浪涌"模拟秒杀：第 1 波 100 人、隔 30 秒第 2 波 200 人、再隔 30 秒第 3 波 500 人"
Arrivals Thread Group控制每秒请求数"不管多少人，每秒稳定发 100 个请求"

日常压测用标准线程组就够了。需要阶梯加压用 Concurrency TG，需要控 TPS 用 Arrivals TG。

取样器 (Sampler) — "发什么请求" ​

取样器是压测的核心动作——真正发请求的就是它。

HTTP 请求 (HTTP Request)（使用频率 90%+） ​

一个 HTTP 请求由五要素组成：

协议 + 服务器 + 端口 + 方法 + 路径 = 一个完整的请求
http   localhost  8080   POST   /api/login
参数说明示例
协议http 或 httpshttps
服务器名称或 IP目标主机api.example.com
端口号服务端口443
HTTP 方法GET / POST / PUT / DELETEPOST
路径接口路径/api/login
消息体数据POST/PUT 时传的 JSON{"username":"admin"}
参数GET 请求的 Query String?page=1&size=10

技巧：把协议、服务器、端口抽到「HTTP 请求默认值」里，每个请求只写方法和路径，少敲很多重复内容。

其他取样器 ​

取样器什么时候用
JDBC 请求 (JDBC Request)直接对数据库执行 SQL，测数据库性能
JSR223 取样器 (JSR223 Sampler)写 Groovy 脚本自定义请求逻辑
TCP 取样器 (TCP Sampler)测自定义 TCP 协议
WebSocket（插件）测实时通信应用（聊天、推送）
OS 进程取样器 (OS Process Sampler)调用系统命令

90% 的场景只用 HTTP 请求和 JDBC 请求，其他的用到再查。

配置元件 (Config Element) — "一次配置，到处复用" ​

口诀：默头管 C 数——默认值、请求头管理器、Cookie 管理器、CSV 数据、计数器。

HTTP 请求默认值 (HTTP Request Defaults) ​

把公共的协议、服务器、端口写在这里，同作用域下的所有 HTTP 请求自动继承：

参数值
协议https
服务器名称或 IPapi.example.com
端口号443

之后每个 HTTP 请求只需填方法和路径，三个字段留空即可。

HTTP 信息头管理器 (HTTP Header Manager) ​

统一管理请求头。第三章已经用过了——一个设 Content-Type，一个设 Authorization。

多个 Header Manager 可以共存，JMeter 自动合并。同名头以离请求最近的那个为准（近优先）。

HTTP Cookie 管理器 (HTTP Cookie Manager) ​

自动处理 Cookie：服务器返回的 Set-Cookie 自动存储，后续请求自动带上。每个线程有独立的 Cookie 存储，模拟不同用户的登录状态。

CSV 数据文件设置 (CSV Data Set Config)（参数化核心） ​

从文件读取测试数据，实现"不同用户用不同账号登录"：

csv
# 文件：users.csv
username,password
user001,pass001
user002,pass002
user003,pass003
配置项值说明
文件名users.csv放在 JMeter bin 目录下或写绝对路径
变量名称username,password逗号分隔，对应 CSV 的列
忽略首行TrueCSV 第一行是标题就勾上
遇到 EOF 是否循环True数据用完了就从头开始
共享模式所有线程每个线程取不同行，不重复

引用方式：${username}、${password}

用户定义的变量 (User Defined Variables) ​

放全局常量，比如环境地址、版本号。适合值不变的小数据。

后置处理器 (Post-Processor) — "从响应里捞数据" ​

这一步叫关联（Correlation），是压测脚本里最重要的操作。

三种最常用的提取器 ​

提取器适合什么响应表达式示例
JSON 提取器 (JSON Extractor)JSON$.data.token
正则表达式提取器 (Regular Expression Extractor)任意文本token=([a-f0-9]{32})
边界提取器 (Boundary Extractor)有明确前后标记左 csrf" value=" 右 "

JSON 提取器 (JSON Extractor) 详解 ​

参数说明示例
创建的变量名称提取后存到哪个变量token
JSON Path 表达式定位要提取的字段$.data.token
默认值提取失败时用的兜底值NOT_FOUND

JSON Path 速查：

表达式取什么
$.token根下的 token
$.data.iddata 下的 id
$.items[0].nameitems 数组第一项的 name
$.items[*].iditems 数组所有项的 id

正则表达式提取器 (Regular Expression Extractor)（兜底方案） ​

当响应不是 JSON 时用。比如从 HTML 页面提取隐藏字段：

响应内容：<input type="hidden" name="csrf_token" value="a8f3b2c1e5">

正则表达式：name="csrf_token" value="([^"]+)"
模板：$1$
变量名：csrf_token
  • 括号 () 里的是要提取的内容
  • $1$ 表示取第一个括号的匹配结果
  • 引用：${csrf_token}

关联三步走 ​

1. 找 → 看响应里哪个字段是动态的（token、sessionId）
2. 提 → 加对应的提取器，设好表达式和变量名
3. 用 → 后续请求里用 ${变量名} 引用

断言 (Assertion) — "验证结果对不对" ​

压测时不仅要看快不快，更要看对不对。全部返回 500 错误还以为系统很快，那就闹笑话了。

最常用的两种 ​

响应断言 (Response Assertion) — 检查状态码或响应内容

配置值含义
测试字段响应代码检查 HTTP 状态码
模式匹配规则相等精确匹配
要测试的模式200期望返回 200

持续时间断言 (Duration Assertion) — 检查响应时间

配置值含义
持续时间（毫秒）3000超过 3 秒就标记失败

断言性能损耗分级 ​

损耗断言类型压测建议
极低持续时间断言 (Duration Assertion)、大小断言 (Size Assertion)✅ 放心用
中响应断言 (Response Assertion)（只断言状态码）✅ 可以用
高JSON 断言 (JSON Assertion)、XPath 断言 (XPath Assertion)、HTML 断言 (HTML Assertion)⚠️ 仅调试时用

定时器 (Timer) — "模拟真实用户的停顿" ​

真实用户不会连续狂点。操作之间有思考时间：看页面、填表单、犹豫。

定时器在每个请求之前执行，多个定时器会叠加。

定时器行为推荐度
均匀随机定时器 (Uniform Random Timer)在一个范围内随机停顿⭐⭐⭐⭐⭐
高斯随机定时器 (Gaussian Random Timer)大部分时间停差不多，少数特别快/慢⭐⭐⭐⭐
固定定时器 (Constant Timer)每次停一样长⭐（仅调试）
同步定时器 (Synchronizing Timer)等人凑够再一起冲（集合点）⭐⭐⭐
常数吞吐量定时器 (Constant Throughput Timer)控制每秒发多少请求⭐⭐⭐

均匀随机定时器 (Uniform Random Timer) 配置 ​

随机延迟最大时间：2000 毫秒
固定延迟：500 毫秒

→ 每次请求前停顿 500ms ~ 2500ms 之间的随机值

同步定时器 (Synchronizing Timer)（集合点） ​

秒杀场景的关键——让一批用户同时触发请求：

模拟用户组的数量：50   ← 凑够 50 人就一起放
超时时间：5000 毫秒    ← 等了 5 秒人还不够也放

→ 制造瞬时并发尖峰

逻辑控制器 (Logic Controller) — "控制请求的执行顺序" ​

默认情况下请求从上到下依次执行。控制器可以改变这个行为。

控制器一句话典型场景
简单控制器 (Simple Controller)纯分组，没逻辑把相关请求放一个文件夹里
If 控制器 (If Controller)条件成立才执行"上个请求成功才继续"
While 控制器 (While Controller)循环直到条件不成立"一直查状态直到返回'完成'"
事务控制器 (Transaction Controller)多个请求打包计时"登录+搜索+下单"算一笔总耗时
吞吐量控制器 (Throughput Controller)按比例分配"80% 流量查商品，20% 下单"
交替控制器 (Interleave Controller)子请求轮流执行"每人只做一个操作，轮流来"

事务控制器 (Transaction Controller) 的用法 ​

事务控制器（名称：完整下单）
  ├── 登录
  ├── 搜索商品
  ├── 加购物车
  └── 提交订单

→ 报告里多一行"完整下单"，显示整个流程端到端耗时
→ 四个请求全部成功，事务才算成功

监听器 (Listener) — "看结果" ​

监听器干什么正式压测
察看结果树 (View Results Tree)逐个看请求/响应详情❌ 必须关
汇总报告 (Summary Report)平均、最快、最慢、错误率、吞吐量✅
聚合报告 (Aggregate Report)额外含中位数、90%/95%/99% 线✅
用表格察看结果 (View Results in Table)表格形式看每次请求❌
图形结果 (Graph Results)折线图❌

铁律：正式压测只保留汇总报告或聚合报告，其他全关。监听器消耗内存，会让压测结果失真。

小结 ​

这一章拆解了八类元件，按执行顺序排列：

元件核心作用记忆点
线程组 (Thread Group)定义用户模型标准够用，阶梯用插件
取样器 (Sampler)发请求HTTP 请求覆盖 90% 场景
配置元件 (Config Element)复用公共配置默头管 C 数
后置处理器 (Post-Processor)提取动态值关联三步走：找 → 提 → 用
断言 (Assertion)验证结果状态码 + 响应时间就够了
定时器 (Timer)模拟思考时间均匀随机最常用
逻辑控制器 (Logic Controller)控制流程事务控制器最实用
监听器 (Listener)看结果调试开，压测关

实际工作中 80% 的时间只跟其中四类打交道：取样器 (Sampler)、配置元件 (Config Element)、后置处理器 (Post-Processor)、监听器 (Listener)。其他的随用随查。

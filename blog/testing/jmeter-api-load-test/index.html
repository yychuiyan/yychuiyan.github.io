性能测试JMeter接口压测Bearer TokenHTML报告

用 JMeter 压一把接口 ​

最近拿本地练习站 testing-online 把接口压测链路又过了一遍：Bearer 登录、关联 Token、压 POST /api/perf/generate，再用 10 / 20 / 50 三档并发对比，最后用命令行出 HTML 报告。

一、这次压什么 ​

项选择
被测环境http://localhost:3001
鉴权POST /api/auth/login → Authorization: Bearer <token>
压测接口POST /api/perf/generate（批量生成用户数据）
Body{"type":"users","count":2}
清理POST /api/perf/clear，{"type":"users"}

为什么选 generate，而不是用户列表？

  • 列表是读接口，RT 往往虚低
  • generate 一次写入一批数据，更能体会「并发 × 单次成本」
  • 跑完还能 clear，适合反复练场景对比

二、从 0 到 1：脚本搭建 ​

目标结构三句话：先登录、再加压、最后清理。下面按点击顺序搭，搭完左侧树应大致如下：

text
Test Plan
├── HTTP 请求默认值                 localhost:3001
├── HTTP 信息头管理器               Content-Type: application/json
├── setUp 线程组 — 登录获取 token
│   └── 登录 POST /api/auth/login
│         ├── JSON 提取器           $.data.token → token
│         └── JSR223                props.put("AUTH_TOKEN", vars.get("token"))
├── 线程组 — 生成用户压测
│   ├── Header                      Authorization: Bearer ${__P(AUTH_TOKEN)}
│   └── POST /api/perf/generate
│         ├── 响应断言              200
│         └── JSON 断言             $.success == true
├── tearDown 线程组 — 后置清理
│   └── POST /api/perf/clear
├── 察看结果树（调试用）
└── 聚合报告

准备工作 ​

  1. 本机启动 testing-online 后端，确认 http://localhost:3001 可访问
  2. 打开 JMeter，保存空计划：Cmd+S → 例如 users-generate.jmx

所有添加操作都是：右键节点 → 添加 → …

步骤 1：HTTP 请求默认值 ​

右键 测试计划 → 添加 → 配置元件 → HTTP 请求默认值

参数值
协议http
服务器名称或 IPlocalhost
端口号3001

后面每个 HTTP 请求只填「方法 + 路径」即可，不用重复写主机端口。

步骤 2：全局 HTTP 信息头管理器 ​

右键 测试计划 → 添加 → 配置元件 → HTTP 信息头管理器

名称值
Content-Typeapplication/json

登录、generate、clear 都是 JSON Body，全局带上最省事。

步骤 3：setUp 线程组（只跑登录） ​

右键 测试计划 → 添加 → 线程（用户）→ setUp 线程组

参数值
名称登录获取 token
线程数1
Ramp-Up0
循环次数1

用 setUp 而不是普通线程组，是为了保证登录一定先于业务执行。

步骤 4：登录 HTTP 请求 ​

右键 setUp 线程组 → 添加 → 取样器 → HTTP 请求

参数值
名称登录请求
方法POST（不要选 GET）
路径/api/auth/login
消息体数据{"username":"炊烟1号","password":"admin123"}

注意：JSON 填在底部 「消息体数据」 大文本框，不是上面的「参数」表。

成功响应（节选，permissions 等字段略）：

json
{
  "success": true,
  "message": "登录成功",
  "data": {
    "username": "炊烟1号",
    "token": "token-admin-001",
    "role": "admin"
  }
}

Token 在 data.token。

步骤 5：JSON 提取器拿 Token ​

右键「登录请求」→ 添加 → 后置处理器 → JSON 提取器

参数值
名称提取 Token
引用名称token
JSON Path 表达式$.data.token
默认值NOT_FOUND

写错成 $.token 时，后面业务会全是 401。

步骤 6：JSR223 把 Token 存成全局属性 ​

setUp 里的普通变量 ${token} 默认传不到后面的业务线程组，需要写成 JMeter 属性：

右键「登录请求」→ 添加 → 后置处理器 → JSR223 PostProcessor 语言选 groovy，脚本：

groovy
props.put("AUTH_TOKEN", vars.get("token"))

业务组稍后用 ${__P(AUTH_TOKEN)} 读取。

步骤 7：业务线程组 ​

右键 测试计划 → 添加 → 线程（用户）→ 线程组

参数冒烟建议正式再改
名称生成用户压测保持
线程数110 / 20 / 50
Ramp-Up15
循环次数1永远（配合调度器持续 10 秒）

命名写清楚，报告里才不会和「用户信息」之类混淆。

调度器在哪里： 线程组面板底部有「调度器」勾选框，勾上后才能填「持续时间（秒）」。冒烟阶段保持循环 1，不用管它；正式压测改成「永远」+ 持续 10 秒。只选「永远」而不勾调度器，它会一直跑到你手动停。

步骤 8：业务组认证头 ​

右键业务线程组 → 添加 → 配置元件 → HTTP 信息头管理器

名称值
AuthorizationBearer ${__P(AUTH_TOKEN)}

这里只加了 Authorization，Content-Type 在全局 Header 里。

步骤 9：生成用户 HTTP 请求 ​

右键业务线程组 → 添加 → 取样器 → HTTP 请求

参数值
名称生成用户
方法POST
路径/api/perf/generate
消息体数据{"type":"users","count":2}

count 单次上限 50000（超出会被截断）。这里一律填 2：并发压测用「永远 + 持续 10 秒」，请求次数极多，单次写入条数直接决定数据总量——50 并发那档实测打了 12.3 万次请求，乘 2 已是 25 万+ 条，本机内存吃紧；若填 100 就是千万级，直接爆。冒烟时若嫌 2 条看不出效果，临时改 10 即可，正式压测前改回 2。

步骤 10：断言（建议加） ​

右键「生成用户」→ 添加 → 断言：

  1. 响应断言：勾选响应代码，模式匹配规则选「等于」，测试模式填 200
  2. JSON 断言：断言 JSON Path 为 $.success，期望值为 true

这样失败会进 Error%，不会「看着绿但业务其实挂了」。

步骤 11：tearDown 清理 ​

右键 测试计划 → 添加 → 线程（用户）→ tearDown 线程组

参数值
名称后置清理
线程数1
循环1

组内同样加 HTTP 信息头管理器：

名称值
AuthorizationBearer ${__P(AUTH_TOKEN)}

再加 HTTP 请求：

参数值
名称清理用户
方法POST
路径/api/perf/clear
消息体数据{"type":"users"}

跑完自动清掉压测用户，只留演示账号。

步骤 12：监听器 ​

右键 测试计划（或业务线程组）→ 添加 → 监听器：

监听器用途什么时候用
察看结果树看单次请求/响应、断言失败原因仅调试 / 冒烟
聚合报告样本数、平均、中位数、90%/95%/99%、异常%、吞吐量仅调试 / 小规模验证
汇总报告只看总体概况，没有百分位列一般不必加

两点别搞错：

  1. 汇总报告和聚合报告列不一样。 汇总报告只有 # 样本 / 平均值 / 最小值 / 最大值 / 标准偏差 / 平均字节数 / 异常 % / 吞吐量 / 接收 KB/sec / 发送 KB/sec；想看 90% / 95% / 99% 百分位，必须加聚合报告。
  2. 正式跑时这些监听器一个都别留。 JMeter 官方最佳实践写得很直白：「Use as few Listeners as possible; if using the -l flag as above they can all be deleted or disabled.」监听器要在压测过程中消费每个样本、在内存里累积统计，吃的是压测机自己的资源；本机练习尤其吃亏——JMeter 和被测服务在同一台机器上。

步骤 13：先冒烟再加压 ​

  1. 业务线程组保持 1 线程 × 1 循环
  2. 点绿色 ▶
  3. 打开察看结果树，确认三步都通：
    • 登录：200，能看到 data.token
    • 生成用户：200，success: true
    • 清理用户：200
  4. 冒烟通过后，再改线程数做 10 / 20 / 50 场景

若点启动「没反应」：多半是没加察看结果树，setUp 一瞬间跑完，界面上看不出来。

补充说明 ​

  • 线程组顺序：登录用 setUp、清理用 tearDown 即可；若三者都是普通线程组，请在测试计划勾选「独立运行每个线程组」，否则可能并行抢跑。
  • 跨组 Token：业务头必须是 Bearer ${__P(AUTH_TOKEN)}，不是 ${token}。

三、线程、Ramp-Up、循环、持续时间 ​

这四个参数最容易混，用一句话分开：

参数管什么
线程数同时有多少虚拟用户
Ramp-Up这些人多久内到齐
循环次数每人把脚本跑几遍
持续时间整场营业多久（常配合「永远」）

循环 vs 持续时间 ​

  • 只要「每人打 1 次」→ 循环 = 1，不必开持续时间
  • 要「压一段时间」→ 永远 + 持续时间

做并发对比时必须选第二种。 循环为 1 配快速接口，线程打完就退出，几个线程实际只有 1 个在跑，测的是串行不是并发。

勾了永远再设持续 10 秒时，总请求数 ≈ 线程数 × 存活期间能打多少次，会远大于线程数——这是正常的。

Ramp-Up 大还是小 ​

  • 偏小：人几乎同时冲进来，偏浪涌
  • 偏大：慢慢进场，更像日常负载

压测场景建议 5s 左右，并且不要超过持续时间——Ramp-Up 比持续时间还长的话，测试结束前线程都没到齐，标称的并发数是虚的。

四、标准场景：10 / 20 / 50 并发 ​

三档分开跑，每次只改线程数一个参数，其余全部保持不变——变量唯一，对比才有意义。

统一的配方 ​

参数值说明
线程数10 / 20 / 50唯一要改的就是它
Ramp-Up5s5 秒内线程全部到齐
循环永远（勾选）线程打完不退出，持续发请求
调度器勾选，持续时间 10 秒压满 10 秒后停止
count2每次只写 2 条，控制内存
登录/清理1 线程 × 1 次不动

三档对应的并发水位：

档位实际并发用途
10 并发10轻度，日常水位
20 并发20中度，看 RT 是否劣化
50 并发50重度，探吞吐的上限在哪

为什么用「永远 + 持续时间」而不是「循环 1」？ 这是最容易埋的坑——循环为 1 配快速接口时，线程打完立刻退出，10 个线程实际只有 1 个在跑，根本测不出并发。

执行顺序 ​

  1. GUI 用 1 线程冒烟，确认登录 + generate + clear 都通
  2. 把所有 GUI 监听器禁用或删除，Cmd+S 保存 jmx
  3. 冒烟通过后切命令行，三档依次跑，每档只改线程数
  4. 每档之间确认清理完成，再跑下一档

提示：GUI 跑和命令行跑不是一回事。 GUI 点 ▶ 适合冒烟调试，真正的压测数字建议用命令行跑。

五、GUI 运行 vs 命令行运行 ​

搭好脚本后，正式跑之前先分清这两种执行方式——它们不是一回事。

GUI（点 ▶）命令行（-n）
本质一边压测一边渲染界面只跑压测，不渲染
资源占用JMeter 界面和被测服务抢 CPU / 内存省下的资源都用于施压
结果监听器挂着监听器（尤其察看结果树）吃内存不加载界面监听器，更接近真实压力
数据可信度线程一多，测出来的数字偏悲观相对更准，适合正式对比
适合场景调脚本、看单次响应10 / 20 / 50 并发对比、出报告

推荐做法：

  1. GUI 只用来搭脚本 + 冒烟（1 线程 × 1 循环，开察看结果树确认三步都通）
  2. 调通后把所有 GUI 监听器禁用或删除（不只是察看结果树），Cmd+S 保存 .jmx
  3. 正式跑三档都切到命令行，分别输出报告目录：
bash
# 每档只改线程数（10 / 20 / 50），其余参数保持不变
jmeter -n -t users-generate.jmx -l result-10.jtl -e -o report-10
jmeter -n -t users-generate.jmx -l result-20.jtl -e -o report-20
jmeter -n -t users-generate.jmx -l result-50.jtl -e -o report-50

用浏览器打开 HTML 报告对比，而不是在 GUI 监听器里读数字。

参数含义：-n 非 GUI、-t 测试计划、-l 结果文件、-e 生成报告、-o 报告输出目录。命令在保存 .jmx 的目录下执行（或把 -t 写成绝对路径）；-o 目录不能已存在。

一句话：GUI 用来写，命令行用来跑，HTML 用来看。 本机练习尤其明显——界面渲染本身就可能占掉一两个并发的能力。

三档跑完，HTML 报告里的 Statistics 表长这样（它是所有报告里列最全的一张表）：

10并发

20并发

50并发

六、报告怎么看 ​

GUI 监听器：只用于调脚本和小规模验证 ​

正式跑的三档数据全部来自 HTML 报告——GUI 里那几张表，正式压测时应该已经删掉了。它们只适合调脚本、小并发（1~2 线程）快速验证时扫一眼：监听器要在压测过程中累积统计，行数一多就吃内存，还会和被测服务抢 CPU。

真要临时看一眼，加聚合报告（汇总报告没有百分位列），盯「生成用户」那一行：

列先看什么
异常 %必须先是 0
# 样本是否远大于线程数（证明是真并发）
平均值、P9050 比 10 涨了多少
吞吐量是否随并发上涨——不涨就是到顶了

登录、清理行的 RT 可以忽略，别和业务行混读。

命令行：HTML 报告 ​

-e -o 会在跑完压测后顺带把 HTML 报告生成到指定目录，不用跑两遍。

如果之前只跑了 -l 没加 -e -o，可以拿现成的 .jtl 单独补报告（这条不重新压测）：

bash
jmeter -g result-10.jtl -o report-10

浏览器打开 report-10/index.html / report-20/index.html / report-50/index.html：

位置看什么
APDEX把响应时间折算成 0~1 的满意度分数，适合对外汇报
Statistics按标签分行，对比业务请求的 Avg / P90 / P95 / Error% / TPS
Active Threads Over Time活跃线程数——验证并发是否真的达到了目标线程数
Response Times Over TimeRT 是否随时间爬升
Errors有失败时看原因

压测时先看 Active Threads Over Time：曲线没爬到目标线程数，说明 Ramp-Up 太长或测试提前结束了，后面的 RT / TPS 都不可信。

-o 目录已存在会报错，删掉旧目录或加 -f。

七、对比时怎么下判断 ​

现象含义
Error% = 0，P95 略升正常，并发高了稍慢
Error% > 0先修脚本/鉴权/断言，别谈性能
P95 涨很多、吞吐几乎不涨接近瓶颈（本机练习站很常见）
样本数对不上检查循环、是否勾了永远、是否中途停止

记住：这里比的是相对差异（10 → 20 → 50 各档之间差多少），不是「系统能扛多少线上用户」。

八、三档跑完，看到了什么 ​

三档按上面的配方各跑一遍（都是跑满 10 秒，峰值线程数也确实是 10 / 20 / 50），数据摆在一起是这样：

档位样本数吞吐量/s平均P90P95P99最大值
10 并发130,28013,0270.58ms1ms1ms2ms5ms
20 并发127,70012,7661.18ms2ms3ms3ms26ms
50 并发123,48612,3213.04ms5ms5ms7ms14ms

HTML 报告里 pct1 / pct2 / pct3 分别对应 90th / 95th / 99th 百分位，别看到 pct1 就当成 P95。

反常的地方：吞吐不涨，延迟涨 ​

按直觉，并发从 10 加到 50，吞吐应该跟着涨。实际是：

  • 吞吐几乎不动：13,027 → 12,766 → 12,321，甚至略微下降
  • 延迟成倍上涨：平均 0.58 → 1.18 → 3.04ms，P90 从 1ms 涨到 5ms

这说明系统已经饱和了——再加线程压不出更多处理能力，多出来的并发只能排队，表现就是延迟变高。

看每秒明细更直观 ​

把 .jtl 按秒切开，看每秒处理了多少请求、平均延迟多少：

时间10 并发（请求/延迟）20 并发（请求/延迟）50 并发（请求/延迟）
第 1 秒13,294 / 0.24ms13,246 / 0.47ms10,422 / 1.43ms
第 3 秒13,378 / 0.54ms13,679 / 1.04ms12,598 / 2.78ms
第 5 秒14,174 / 0.69ms12,728 / 1.56ms13,886 / 3.59ms
第 7 秒14,461 / 0.68ms13,929 / 1.42ms13,633 / 3.65ms
第 9 秒14,180 / 0.69ms13,512 / 1.47ms14,074 / 3.54ms

三档最后都稳定在 1.3～1.4 万/秒，谁也不比谁高。而且延迟从第 5 秒（Ramp-Up 结束）起就平了，不再往上爬——这排除了「数据越积越多拖慢服务」的可能，剩下的解释就是纯粹的排队。

用 Little 定律算一下 ​

排队论里有个很直观的关系：

在途请求数 = 吞吐量 × 延迟

代入三档数据（延迟换算成秒）：

档位计算服务端在途请求占线程数
1013027 × 0.0005787.575%
2012766 × 0.00117615.075%
5012321 × 0.00303637.475%

比值都稳定在 75%。这验证了两件事：

  1. 线程数确实转化成了并发（剩下 25% 的时间花在客户端和网络上），不是「循环 1」那种假并发
  2. 多出来的并发全部排进队列、变成了延迟，而不是更强的处理能力

为什么卡在 1.3 万 ​

这台练习站是 Express + Node.js，几个现实约束：

  1. Node.js 单线程事件循环：所有请求在一个 CPU 核心上排队。1.3 万/秒 ≈ 每请求 77µs CPU，对「解析 JSON + 序列化响应 + push 数组」来说基本是单核上限
  2. JMeter 和被压服务同一台机器：线程越多，JMeter 自己吃掉的 CPU 越多，反过来挤压服务端——这就是 50 并发吞吐反而略低的原因
  3. 数据无界增长：一轮 13 万次请求 × 每次 2 条 = 26 万个对象堆在内存里，GC 压力会随测试推进增加

顺带排查过一个疑点：鉴权中间件里有 users.find()，看着像 O(n)。但管理员账号在数组第 0 位，find 立刻返回，实际是 O(1)，不是瓶颈。

这个结论比「堆线程」值钱 ​

  • 10 并发时其实已经到顶了，后面两档只是把队列拉长
  • 真要提升得先解决单核瓶颈（多进程 / cluster / 换一台压测机），而不是继续加线程
  • 本机练习站的饱和点跟线上服务没有任何关系，结论只能做相对参考

压测的目标不是把线程数堆高，而是找到那个「再加线程也不再涨」的拐点。这次很幸运，10 并发就摸到了。

九、固定循环 vs 持续时长 ​

为什么并发场景要用「永远 + 持续时间」，而不是「循环 1」？这次踩得最深的坑就在这里。

循环 = 1 时，其实没有并发 ​

线程数 10、Ramp-Up 5s、循环 1 跑一遍，从 .jtl 里看线程的时间戳：

text
生成用户压测 1-1    t = 0.00s
生成用户压测 1-2    t = 0.50s
生成用户压测 1-3    t = 1.00s
...
生成用户压测 1-10   t = 4.50s

Ramp-Up 把 10 个线程按 500ms 一个依次放出来，而每个线程打完一个请求（约 3ms）就结束了。所以任意时刻只有一个线程在跑——看 .jtl 的 grpThreads 列（当前活跃线程数），全程都是 1。

报告里 #Samples = 10 看着没错，但那是 4.8 秒里串行打出来的 10 次，不是 10 个用户同时在线。

永远 + 持续时长才是真并发 ​

改成「永远 + 持续 10 秒」后，线程打完不退出，5 秒后全部存活。同样看 grpThreads：

配置峰值并发线程
循环 1 + Ramp-Up 5s1
永远 + 持续 10s等于线程数

这才是真的在压「N 个用户同时在用」。

两种配置怎么选 ​

循环 = 1（固定次数）永远 + 持续 10s
线程存活打完即退一直活着
实际并发常常只有 1≈ 线程数
样本数≈ 线程数由吞吐决定，很多
适合冒烟、验证脚本连通性并发 / 负载对比

Ramp-Up 别超过持续时间。 Ramp-Up 设 15s、持续只有 10s 时，测试在第 10 秒就结束，线程还没启动完（实测峰值只到 34 个）——名义 50 并发，实际只有 34。

持续压还多一个观察点：Response Times Over Time 那条线。前半段平稳、后半段开始上翘，通常说明有资源在累积（内存、连接、GC），这类问题短压测看不出来。

注意 ​

  1. 跑完确认 tearDown 清理成功（持续压会造大量用户）
  2. 正式跑时把 GUI 监听器全部禁用或删除（官方最佳实践：用了 -l 就都可以删掉），只看命令行生成的 HTML 报告
  3. 本机练习站结论仍是相对参考，不代表线上容量

小结 ​

接口压测在 JMeter 里，真正要固化的不是元件清单，而是习惯：

  1. 鉴权一次、业务反复、收尾清理
  2. 并发档位分开跑、参数只改一处
  3. GUI 调通，CLI 出数
  4. 先看 Error%，再看 P95 和吞吐
  5. 吞吐不再随并发上涨，就是到拐点了——继续加线程只会加延迟
  6. 练习站结论只做相对对比

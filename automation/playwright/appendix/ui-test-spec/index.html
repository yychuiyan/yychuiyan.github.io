业务平台 UI 自动化测试用例 ​

一、基本概念 ​

1.1 优先级与测试分层 ​

优先级含义对应测试层执行策略执行时机
P0核心主流程，阻塞性冒烟测试CI 门禁必跑，每次提交/PR 触发每次构建
P1重要功能，回归必测回归测试回归流水线每日跑每日/发版前
P2边界场景、低频操作全量测试发版前跑一次大版本发布

1.2 三层关系 ​

全量测试 ───────────────────────── P0 + P1 + P2
  ├── 回归测试 ─────────────────── P0 + P1
  │     └── 冒烟测试 ───────────── P0
  • 冒烟是回归的子集，回归是全量的子集
  • 跑回归 = 跑冒烟（P0）+ 功能验证（P1）
  • 跑全量 = 回归（P0+P1）+ 边界场景（P2）
  • 不存在"只跑 P1 跳过 P0"的情况

1.3 这不是国际标准，是行业共识 ​

IEEE 829、ISTQB 等正式标准未定义"P0=冒烟 P1=回归 P2=全量"的映射关系。但互联网公司普遍约定俗成使用此划分，属于行业最佳实践。关键不在于标签叫什么，而在于团队内部达成一致并写进文档。

二、用例表字段与编写规范 ​

2.1 完整版（推荐，10 列） ​

适合正式项目、多人协作、需要追踪自动化覆盖率。

2.2 最小够用版（6 列） ​

适合小团队、敏捷项目、快速上手。

前置条件、自动化状态、备注可以写在步骤里或口头同步，量不大时心里有数就行。

2.3 字段标准说明 ​

以上字段并非某个国际标准（如 IEEE 829）的照搬，而是行业约定俗成的实践。核心 6 列（序号、模块、标题、优先级、步骤、预期）是所有测试团队用例表的最大公约数，无论手工还是自动化、UI 还是接口，都离不开这 6 个字段。其余列根据项目需要增减即可。

2.4 自动化状态定义 ​

状态含义
已自动化脚本已写好，对应 spec 文件可查
待自动化计划写但还没写
不适合自动化验证码、人脸识别、一次性数据等场景

2.5 测试用例命名规范 ​

统一的命名让用例列表一目了然，也方便 --grep 按关键字筛选。推荐格式：

[模块] | [场景] | [预期结果]

// ✅ 推荐：三段式，grep 友好
test('登录 | 正确账号密码 | 跳转首页', ...)
test('登录 | 密码错误 | 提示错误信息并停留', ...)
test('任务管理 | 名称为空 | 创建失败提示必填', ...)

// ❌ 避免：无意义命名
test('test1', ...)
test('登录测试', ...)            // 不知道测哪个场景
test('admin_login_works', ...)   // 中英混用，不一致

命名规则：

规则说明示例
三段式模块 | 场景 | 预期，用 | 分隔登录 | 密码错误 | 提示错误
模块在前与用例表的"模块"列对齐，方便 grep--grep "登录" 捞出所有登录用例
场景具体不写"正常测试"，写"正确账号密码"一眼知道和旁边用例的区别
结果可观测断言什么就写什么"跳转首页"比"成功"更明确
同一 describe 不重复模块名describe 已标注模块，test 只写 场景 | 结果describe('登录', () => { test('正确密码 | 跳转首页', ...) })

注意： Playwright 的 --grep 对 test() 标题做正则匹配，所以命名规范直接决定筛选效率。命名混乱 = grep 废掉。

2.6 用例设计覆盖维度 ​

设计用例时，对照下面 checklist 自查是否遗漏关键场景。不只是"能跑通就行"。

维度必须覆盖说明优先级
正常流程✅主路径走通，最核心的用户操作链P0
异常校验✅空输入、格式错误、超限输入、非法值P1
边界值✅最小值、最大值、刚好临界（如 0 字符、200 字符上限）P1
空状态建议无数据时页面的空状态提示（非报错）P1
加载状态建议数据加载中的骨架屏/spinner、超时处理P2
权限拦截✅未登录访问、无权限用户访问受保护页面P1
并发/重复建议快速双击按钮、重复提交表单、同时操作P2
数据变更后建议增删改后列表刷新、详情同步更新P1

设计原则：先覆盖"能不能用"（P0 正常流程），再覆盖"会不会错"（P1 异常校验），最后覆盖"好不好用"（P2 边界体验）。

示例——登录模块覆盖检查：

维度对应用例
正常流程TC-001 管理员账号登录成功跳转首页
异常校验TC-002 密码错误提示错误信息
权限拦截TC-003 未登录直接访问受保护页面
边界值密码长度上限、特殊字符账号（可扩展 P2）
空状态首次登录引导（按项目实际决定）

四、测试文件组织结构 ​

4.1 组织方式对比 ​

组织测试用例有两种主流方式：目录分离 和 标签标记。

维度目录分离标签标记
原理按优先级建文件夹，P0 放 smoke/，P1 放 regression/所有用例放一起，用 tag 标记优先级
CI 命令npx playwright test tests/smoke/npx playwright test --grep "@p0"
代码重复P0 在两个目录各写一份一份代码，标签区分
新人理解打开目录名就知道需要了解标签约定
框架依赖无，换个框架也能用依赖 Playwright tag 语法
灵活性临时筛选要移动文件--grep-invert 一键跳过
企业主流度老项目过渡用⭐ 当前主流

4.2 新项目推荐：目录 + 标签，双管齐下 ​

目录按优先级分层，标签做精细化过滤，两者互补：

tests/
├── smoke/                      ← 冒烟专用（只放 P0）
│   ├── login.spec.ts           ← 仅 P0 场景
│   ├── batch.spec.ts
│   └── scoring.spec.ts
│
├── regression/                 ← 回归专用（只放 P1）
│   ├── login.spec.ts           ← 仅 P1 场景
│   ├── batch.spec.ts
│   └── scoring.spec.ts
│
└── edge/                       ← 边界场景（P2，可选）
    ├── login.spec.ts
    └── batch.spec.ts

4.3 必须遵守的约束 ​

一个 spec 文件内不跨优先级。 P0 和 P1 不在同一个文件，避免冒烟执行时带上不该跑的用例。

4.4 如何避免定位器重复维护 ​

同一个模块的 P0 和 P1 分别在两个目录，但都引用同一个 Page Object：

pages/
└── LoginPage.ts                    ← 定位器只写这里（唯一真源）

tests/
├── smoke/
│   └── login.spec.ts               ← import LoginPage
└── regression/
    └── login.spec.ts               ← import 同一个 LoginPage

改定位器只需改 pages/ 一处，两个目录的 spec 不用动。

4.5 老项目/存量项目：标签是更轻量的选择 ​

如果已有按角色或模块分的目录结构（如本项目），重构目录成本太高，直接用标签即可：

tests/
├── login/           ← 不动现有结构
├── hr/
├── employee/
├── judge/
└── manager/

文件不拆、目录不动，只加标签，靠 --grep 切执行范围。

五、标签（Tag）使用指南 ​

5.1 在测试用例中加标签 ​

  test(

      // 测试逻辑...
    }

  test('审批人登录成功', { tag: ['@p0', '@smoke'] }, async ({ page }) => {
    // 测试逻辑...
  });
});

// tests/regression/login.spec.ts — P1 用例
test.describe('登录-回归', () => {
  test(

      // 测试逻辑...
    }

    '用户名为空不可登录',
    { tag: ['@p1', '@edge'] }, // ← 多个标签用数组

    }

});

5.2 常用标签体系 ​

优先级标签 ​

标签含义使用场景
@p0核心主流程系统最关键路径，挂了等于系统不可用。每次 PR 必跑，不通过禁止合入
@p1重要功能主流程之外的异常、校验、权限场景。回归每日跑，挂了群通知
@p2边界场景低频操作、极端输入、兼容性。发版前跑一次即可

测试分层标签 ​

标签含义使用场景
@smoke冒烟测试等同于 @p0，验证核心链路是否跑通。通常打在 @p0 用例上作为冗余标记，方便 --grep "@smoke" 直接捞
@regression回归测试等同于 @p0 + @p1 的合集，用于每日构建。一般不单独打这个标签，而是执行时用 `--grep "@p0
@edge边界/全量对应 @p2 场景，只在全量跑。如空值、超长输入、并发操作等

业务模块标签 ​

标签含义使用场景
@login登录模块所有登录相关用例，包括正常登录、异常登录、权限拦截
@task任务管理任务的创建、编辑、删除、状态变更
@review审核评价审核打分、评价提交、评价修改
@apply审批申请申请提交、申请查看、审批流程
@record个人记录记录查看、详情展开、空状态

模块标签按实际业务命名，以上为示例。建议团队统一命名后写入文档，避免 @batch 和 @task 混用。

特性标签 ​

标签含义使用场景
@slow慢用例执行时间明显超过平均值的用例（如大数据量、多次等待）。CI 门禁可加 --grep-invert "@slow" 跳过以提速
@flaky不稳定偶发失败的用例（如依赖外部服务、时序敏感）。打了此标签的用例不应卡门禁，需定期修复
@hotfix紧急修复相关与当前紧急修复相关的用例集合。线上出问题时快速圈定范围，只跑相关用例
@deprecated待废弃功能即将下线但暂未删除的用例，执行时可跳过
@wip开发中用例还在编写中，不应在 CI 中执行
@bug:ID关联缺陷复现某个 Bug 的用例，如 @bug:JIRA-1234。Bug 修复后此用例自动转为回归用例

5.3 命令行执行 ​

bash
# 冒烟 —— 只跑 P0
npx playwright test --grep "@p0"

# 回归 —— 跑 P0 + P1
npx playwright test --grep "@p0|@p1"

# 全量 —— 不加过滤，跑所有
npx playwright test

# 回归但跳过不稳定的
npx playwright test --grep "@p0|@p1" --grep-invert "@flaky"

# 只重跑上次失败的 + 冒烟
npx playwright test --grep "@p0" --last-failed

# 只跑某个模块的冒烟
npx playwright test --grep "@p0" --grep "@login"

# 跑冒烟 + 某个紧急修复相关
npx playwright test --grep "@p0|@hotfix"

| 是正则表达式的 "或"，--grep-invert 是排除匹配的用例。

5.4 配进 package.json（推荐） ​

json
{
  "scripts": {
    "test": "npx playwright test",
    "test:smoke": "npx playwright test --grep '@p0'",
    "test:regression": "npx playwright test --grep '@p0|@p1'",
    "test:edge": "npx playwright test --grep '@p2'",
    "test:headed": "npx playwright test --headed",
    "test:ui": "npx playwright test --ui",
    "test:debug": "npx playwright test --debug"
  }
}

日常使用：

bash
npm run test:smoke        # 冒烟
npm run test:regression   # 回归
npm test                  # 全量

六、Jenkins CI 集成 ​

6.1 标签方式（推荐） ​

标签给了 Jenkins 最大的灵活性——不改代码就能调整执行范围：

groovy
// Jenkinsfile
pipeline {
    agent any

    stages {
        stage('安装依赖') {
            steps {
                sh 'npm ci'
                sh 'npx playwright install chromium --with-deps'
            }
        }

        stage('冒烟测试') {
            steps {
                sh 'npx playwright test --grep "@p0"'
            }
            post {
                failure {
                    // 冒烟挂了直接通知，不继续跑回归（浪费资源）
                    emailext(
                        subject: "[冒烟失败] ${env.JOB_NAME} #${env.BUILD_NUMBER}",
                        body: "冒烟测试未通过，请检查：${env.BUILD_URL}",
                        to: 'dev-team@company.com'
                    )
                }
            }
        }

        stage('回归测试') {
            steps {
                sh 'npx playwright test --grep "@p0|@p1"'
            }
        }

        stage('全量测试') {
            when { branch 'release/*' }     // 只有发版分支跑全量
            steps {
                sh 'npx playwright test'
            }
        }

        stage('生成报告') {
            steps {
                sh 'npx allure generate ./reports/allure-results -o ./reports/allure-report --clean'
            }
        }
    }

    post {
        always {
            // 无论成败都归档报告
            publishHTML(target: [
                reportName: 'Playwright Report',
                reportDir: 'reports/playwright-report',
                reportFiles: 'index.html'
            ])
            allure includeProperties: false, results: [[path: 'reports/allure-results']]
        }
    }
}

6.2 目录方式 ​

也可以，但比标签僵硬——想临时跳过某类用例必须改目录结构再 commit：

groovy
stage('冒烟测试') {
    steps {
        sh 'npx playwright test tests/smoke/'
    }
}
stage('回归测试') {
    steps {
        // 注意：回归 = smoke 目录 + regression 目录，不能只跑 regression/
        sh 'npx playwright test tests/smoke/ tests/regression/'
    }
}

6.3 标签在 Jenkins 上的额外优势 ​

场景目录方式标签方式
临时跳过 flaky 用例要注释代码或移动文件--grep-invert "@flaky"
只重跑失败 + P0做不到--grep "@p0" --last-failed
按模块只跑登录目录没按模块分--grep "@login"
并行拆分加速手动分目录--grep "@p0" 配合 shard
紧急补丁只跑相关用例要挪文件--grep "@p0|@hotfix"
不改 Jenkins 配置临时加条件改 Jenkinsfile改命令参数即可

6.4 执行策略建议 ​

PR 提交    → 冒烟（P0）        → 5 分钟内，挂了禁止合入
每日凌晨  → 回归（P0 + P1）    → 20 分钟内，挂了群通知
发版分支  → 全量（P0 + P1 + P2）→ 不限时，全部通过才上线

七、最佳实践总结 ​

原则做法
用例先行写脚本前先列出用例表（Excel/脑图），明确场景和优先级
三层分治冒烟 P0 = CI 门禁，回归 P1 = 每日跑，全量 P2 = 发版跑
新项目按目录分smoke/ regression/ edge/ 三层目录，一个文件不跨优先级
老项目用标签不动现有目录，加 tag 区分优先级，--grep 过滤
标签兜底即使用目录分，也打上 tag，方便报告统计和临时筛选
Page Object 隔离定位器只放 pages/，spec 文件只写业务逻辑，避免重复维护
命令脚本化把执行命令配进 package.json，团队成员统一入口
Jenkins 用标签驱动CI 阶段靠 --grep 切执行范围，不改代码就能调整
文档即标准把这份文档放团队 Wiki，大家按同一个规则来
覆盖率可视化定期更新覆盖率汇总表，缺口一目了然
